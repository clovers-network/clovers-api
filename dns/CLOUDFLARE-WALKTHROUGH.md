# Moving clovers.network to Cloudflare

Two files, both generated by `from-export.mjs` from Netlify's own export:

| File | Use |
|---|---|
| `clovers.network.zone` | The record of truth. 22 records. Read this to know what the zone *is*. |
| `clovers.network.cloudflare.zone` | **Import this one.** Identical minus the apex CNAME, which goes in by hand. |

## Why two files

The apex carries a CNAME alongside MX and TXT records at the same name. That is
illegal under RFC 1034 — a CNAME must be alone at its name. Cloudflare supports
it anyway through CNAME flattening, but its BIND importer's behaviour is
undocumented: it may reject the file, skip the record, or accept it. Rather than
discover which during a migration, the import file omits it and you add one
record by hand. One manual record beats a partial import whose failure mode you
have to reverse-engineer.

Do **not** replace the apex with the A/AAAA addresses Netlify currently answers
with. That was the original mistake — see `DNS-CUTOVER.md`.

## What you need

Access to **Name.com**, the registrar. Not Netlify — Netlify only ever held the
zone *contents*, and those are in `export.csv` now. The domain was renewed on
2026-08-12, so that access exists.

The Cloudflare account is `services@trifle.life`, which already hosts the
`clovers-forum-archive` Pages project.

---

## Step 1 — add the zone (you)

Cloudflare dashboard → **Add a domain** → `clovers.network` → **Free** plan.

Cloudflare will scan and guess at records. **Delete everything it guessed.** Its
scan cannot see what it cannot resolve, and it will model the Netlify apex as
static addresses — the exact error being avoided here.

## Step 2 — import (you)

**DNS → Records → Import and Export → Import DNS records**, and upload
`clovers.network.cloudflare.zone`.

Expect **21 records**. If the count differs, stop and compare against
`clovers.network.zone` before going further.

## Step 3 — add the apex by hand (you)

**DNS → Records → Add record**

| Field | Value |
|---|---|
| Type | `CNAME` |
| Name | `@` |
| Target | `clovers-no-bots.netlify.app` |
| Proxy status | **DNS only** (grey cloud) |
| TTL | Auto |

Cloudflare will note it is flattening the apex. That is expected and correct.

## Step 4 — check every record is grey (you)

Every record must be **DNS only**. Proxying changes TLS termination and adds
caching, and `api.clovers.network` serves a websocket — proxy it by accident and
realtime breaks in a way that looks like an application bug.

Proxying may be worth doing later, deliberately, one record at a time. Not
during a delegation change.

## Step 5 — switch the nameservers (you)

Cloudflare shows two nameservers. At **Name.com**, replace the four
`dns*.p0*.nsone.net` entries with those two.

`clientTransferProhibited` on the domain does not block this — it blocks
transfers between registrars, not nameserver edits.

### A fault this fixes

The registry currently delegates to `dns*.p03.nsone.net`, while the zone itself
publishes `dns*.p07.nsone.net`. Parent and child disagree. It resolves today, but
if NS1 retires the p03 pool the domain breaks with no warning and no obvious
cause.

## Step 6 — verify (me)

Ask and I will run the comparison: all 22 names against the old nameservers and
the new, plus mail specifically. Mailgun MX and DKIM are what actually breaks
people in a DNS move, because nothing appears wrong until a message silently
fails days later.

Propagation is usually minutes to a couple of hours. The old NS1 nameservers
keep answering throughout, so there is no window where the domain is dark.

---

## Then: forum.clovers.network → the archive

Only after the zone is on Cloudflare, because Pages custom domains want the
domain in the same account.

1. **Pages → clovers-forum-archive → Custom domains → Set up a custom domain**
2. Enter `forum.clovers.network`
3. Cloudflare replaces the `A 68.183.74.37` record itself

This makes the **live Discourse unreachable**, which is the intent — the archive
replaces it. Verify the archive first; it is 19 topics and 41 posts, and the
content stops at July 2021 because everything after that was spam.

The droplet at `68.183.74.37` can then be shut down.

## Rolling back

Before step 5, nothing has changed — the zone sits in Cloudflare unused. After
step 5, roll back by restoring the four `dns*.p03.nsone.net` nameservers at
Name.com. Netlify still holds the original zone, so it resumes answering.

Keep `export.csv` regardless. It is the only copy of that zone outside an
account nobody can reach.
